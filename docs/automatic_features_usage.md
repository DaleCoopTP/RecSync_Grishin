# Запуск эксперимента с автоматическими признаками

Пошаговые команды: подготовка, отбор признаков, валидация, фиксация метода,
итоговый тест и проверка случайными наборами. Результаты описаны в
[отчёте](../REPORT.md) и [выполненном ноутбуке](../notebooks/kion_research.ipynb),
правила эксперимента записаны заранее в [протоколе](automatic_features_protocol.md).
Команды baseline вынесены в [отдельную инструкцию](baseline_usage.md).

## Что нужно заранее

Окружение то же, что у baseline (`requirements.lock`), дополнительных
зависимостей нет. Эксперимент использует готовый baseline: подготовленные данные,
кэши кандидатов и признаков, модели и манифесты, включая абляцию групп
признаков. Их версии и контрольные суммы проверяются при запуске.

Модели и данные в Git не хранятся. На новой машине сначала обучите baseline по
[инструкции](baseline_usage.md) и выполните `python -m scripts.feature_ablation`.
Если конфигурация baseline другая, укажите её в поле `baseline_config` файла
`autofeatures.toml`. Сам эксперимент baseline не переобучает и данные не
скачивает.

## Команды по шагам

Из корня проекта:

```bash
.venv/bin/python -m kion_autofeatures prepare
.venv/bin/python -m kion_autofeatures search
.venv/bin/python -m kion_autofeatures validate
.venv/bin/python -m kion_autofeatures freeze
.venv/bin/python -m kion_autofeatures test
.venv/bin/python -m kion_autofeatures verify
```

| Шаг | Что делает |
|---|---|
| `prepare` | проверяет и записывает входные данные baseline |
| `search` | генерирует 504 признака и отбирает их на срезах 19/26 июля с оценкой на 2 августа |
| `validate` | обучает и сравнивает семь заранее заданных вариантов на 9 августа |
| `freeze` | фиксирует метод и контрольные суммы; после этого `search` закрыт |
| `test` | переобучает четыре модели, затем строит тестовые метки и считает метрики |
| `verify` | загружает сохранённые модели и проверяет, что прогнозы и метрики совпадают |

Повторный `test` проверяет готовые результаты и ничего не обучает.

## Полный повтор под новым именем

```bash
.venv/bin/python -m kion_autofeatures reproduce --name reproduction_01
```

Имя должно быть новым, опубликованные результаты не перезаписываются.
Остановиться раньше можно флагом `--through validate`. После прерывания
продолжайте нужной командой с тем же `--name`: готовые шаги используются повторно,
незаконченная модель обучается заново. Если конфигурация, код или артефакт не
совпадают с записанными, команда завершается с ошибкой, а не переобучает
молча. Чтобы изменить метод после `freeze`, нужен новый эксперимент.

## Где лежат результаты

Настройки находятся в `autofeatures.toml`. По умолчанию результаты пишутся
в `results/autofeatures/main`, модели и кэши в `artifacts/autofeatures/main`.

| Файл | Содержимое |
|---|---|
| `inputs.json` | входные данные baseline и их контрольные суммы |
| `selection.json` | отобранные и случайные признаки, их описания, удалённые признаки |
| `validation_results.csv`, `test_results.csv` | метрики вариантов |
| `*_intervals.json` | парные bootstrap-интервалы |
| `test_segments.csv` | метрики по сегментам пользователей |
| `frozen.json` | зафиксированный метод |

Время шагов записывается в UTC. В записи каждой модели отдельно лежат время
построения Pool, обучения и предсказания (медиана трёх прогонов после прогрева),
размер модели и пик памяти процесса. Пик памяти включает загруженные данные,
поэтому это не размер самой модели. Для кэша признаков записано время его
построения; повторное чтение кэша не выдаётся за новый расчёт. Время обучения
baseline взято из исходного запуска и приводится отдельно от новых замеров.

## Ограничения ресурсов

Каждый тяжёлый шаг запускается в отдельном процессе, и одновременно может идти
только один. Лимит: два вычислительных потока и 6 ГБ памяти на процесс вместе
с дочерними (общие страницы могут учитываться дважды). Лимиты потоков ставятся
до импорта числовых библиотек. При превышении памяти процесс останавливается,
готовые шаги сохраняются. Если система не даёт следить за памятью дочернего
процесса, запуск завершается с ошибкой: лимит не отключается молча. Логи и
замеры лежат в `artifacts/autofeatures/<имя>/resources`.

## Тесты и пилот

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m kion_autofeatures --help
```

Тесты работают на маленьких синтетических данных и основной поиск не запускают.

До основного эксперимента выполнен [пилот](automatic_features_pilot.md) на
1 000 пользователях: он проверил весь путь и оценил время и память. Пилот
воспроизводится командой `python -m scripts.autofeatures_pilot` в отдельном
каталоге и использует более ранний, исторический тест.

## Промежуточные отчёты

[Отчёт по валидации](../results/autofeatures/main/VALIDATION.md) и
[отчёт по тесту](../results/autofeatures/main/TEST.md) собираются из готовых
результатов без обучения:

```bash
.venv/bin/python -m scripts.build_autofeature_validation_report
.venv/bin/python -m scripts.build_autofeature_test_report
```

Для другого эксперимента добавьте `--name NAME`. Оба скрипта проверяют, что все
варианты ранжируют одни и те же пары для одних и тех же пользователей и целей.
Отчёт по тесту дополнительно проверяет параметры четырёх переобучений и
совпадение метрик полного baseline с исходной оценкой. Результаты проверок:
[validation_verification.json](../results/autofeatures/main/validation_verification.json),
[test_pre_evaluation_checkpoint.json](../results/autofeatures/main/test_pre_evaluation_checkpoint.json)
(состояние до подсчёта тестовых метрик) и
[test_verification.json](../results/autofeatures/main/test_verification.json).

Повторный `test` только проверяет сохранённое. Новый отбор, оценённый на том же
тесте, независимого подтверждения уже не даст: для этого нужен новый отложенный
период.

## Проверка случайными наборами того же размера

```bash
.venv/bin/python -m scripts.random_subsets   # по умолчанию --draws 20 --extra-seeds 4
```

Проверка выполнена после теста и тестовые данные не использует. Скрипт
восстанавливает данные отбора из кэшей (обучение 19/26 июля, оценка 2 августа)
и сверяет их по SHA-256 с тем, на чём обучался отобранный набор. Затем он
обучает 20 новых случайных наборов по тому же правилу, что и контрольный, но
с другими seed, сам контрольный набор, повтор отобранного набора с seed 42
(должен совпасть до 1e-10) и отобранный набор ещё с четырьмя seed CatBoost.
В конце скрипт проверяет, что зафиксированный метод и тестовые результаты не
изменились. Для другого эксперимента добавьте `--name NAME`; готовые модели при
повторном запуске используются заново.

Модели лежат в `artifacts/autofeatures/main/diagnostics`, итоги в
[random_subsets.json](../results/autofeatures/main/random_subsets.json) и
[random_subsets.csv](../results/autofeatures/main/random_subsets.csv).

## Отчёт и ноутбук

```bash
.venv/bin/python -m scripts.build_research_report
.venv/bin/python -m scripts.build_research_notebook --execute
```

Обе команды читают готовые результаты основного эксперимента из
`autofeatures.toml`. Первая собирает `REPORT.md`, три графика и сводку в
`results/autofeatures/main/report`. Вторая выполняет ноутбук от начала до конца:
пересчитывает признаки для одного пользователя и сверяет их с кэшем, проверяет,
что изменение будущих событий их не меняет, и воспроизводит прогнозы всех 12
сохранённых моделей. Обучение в ноутбуке запрещено, без готовых артефактов он
останавливается. Проверки и контрольная сумма ноутбука записываются в
`notebook_execution.json`, ресурсы в `notebook_resources.json`.

Ноутбук работает в тех же лимитах: два потока и 6 ГБ памяти на процесс вместе
с Jupyter kernel. Без `--execute` создаётся только шаблон в
`artifacts/research_delivery`, выполненный ноутбук не меняется. Отчёт по
baseline `docs/baseline_details.md` собирается отдельно:
`python -m scripts.build_report`.

Полный путь с нуля, включая baseline, описан в
[отчёте](../REPORT.md#8-воспроизведение). Чтобы быстро проверить результаты на
другой машине, нужно либо перенести артефакты с их контрольными суммами, либо
повторить всё обучение.
